Registro y seguimiento de beneficiarios en Urabá

Prototipo web para el flujo Registro → Vinculación → Atención/Ayuda → Seguimiento → Reporte, construido para el reto URABÁ-PAÍS. Este documento resume qué se implementó, cómo está construido, qué datos maneja y qué ve cada tipo de usuario.

Stack Node.js · Express · Firestore · React · TypeScript Estado Prototipo funcional
01

Resumen

La solución organiza toda la información alrededor de una única unidad: el beneficiario. Una misma persona puede participar en varios programas y recibir distintas atenciones, ayudas o seguimientos a lo largo del tiempo, pero conserva un solo registro y un código interno inmutable, evitando duplicados y dispersión de su historial.

El sistema cubre el flujo completo pedido en la guía del reto: se busca a la persona antes de registrarla, se le vincula a uno o varios programas con su propio estado, se registran las atenciones o ayudas que recibe y los seguimientos de su caso, y toda esa información se consolida en una ficha única y en indicadores agregados para la toma de decisiones — siempre con datos ficticios o anonimizados y sin exponer información personal en pantallas o reportes públicos.

02

Requerimientos atendidos

Los cuatro módulos obligatorios

MóduloQué hace la solución
1. Beneficiarios y familias Búsqueda obligatoria por tipo y número de documento antes de crear un registro; si ya existe, se bloquea el duplicado y se abre la ficha existente. Cada persona recibe un codigo_interno único e inmutable. Se puede registrar, consultar y editar datos básicos, y relacionar al menos un integrante familiar. Incluye un flujo aparte para personas sin documento de identidad.
2. Programas y participación Un beneficiario se vincula a uno o varios programas, cada vinculación con su propia fecha y estado (inscrito, en_proceso, finalizado, retirado), sin duplicar a la persona.
3. Atención y seguimiento Registro de atenciones/ayudas ya entregadas (tipo, fecha, descripción, responsable, resultado) y de seguimientos del caso (avance o novedad, observación, acción pendiente, próximo contacto), con evidencia fotográfica opcional adjunta a cada registro.
4. Consultas y reportes Ficha consolidada por beneficiario (datos, familia, programas, historial completo) y tablero con cuatro indicadores dinámicos y agregados — sin datos personales identificables — exportable a PDF.

Componentes complementarios implementados

Acceso y roles

Autenticación con Firebase

Dos roles, administrador y encuestador. El rol se auto-asigna como encuestador al primer ingreso; administrador solo se otorga a mano en la consola.

Sección pública

Página informativa del proyecto

Misión, líneas de trabajo, cómo acceder a un programa y canales de contacto, visible sin iniciar sesión y sin ningún dato personal.

Inteligencia artificial

Asistente conversacional

Resume historiales, busca beneficiarios y lee indicadores usando las mismas rutas autenticadas del backend. No diagnostica ni decide; solo administradores lo ven.

Exportación

Reportes en PDF

El tablero de indicadores se descarga como PDF con la gráfica incluida.

Extensiones no pedidas en la guía

Evidencia fotográfica

Fotos por atención/seguimiento

Se pueden adjuntar una o más fotos a un registro ya creado, almacenadas en Cloudinary; el backend nunca expone sus credenciales al navegador.

Modo sin conexión

PWA con sincronización

Beneficiarios, atenciones y seguimientos se pueden registrar sin internet; quedan en una cola local y se sincronizan solos al recuperar conexión.

Geolocalización

Coordenadas al registrar

Captura opcional de latitud/longitud del dispositivo al crear un beneficiario nuevo.

Fuera de alcance por ahora Accesibilidad ampliada más allá de lo básico, reglas de conteo avanzado por resultado o actividad, y detección automática de duplicados sin documento (hoy requiere validación manual).
03

Arquitectura

Arquitectura cliente-servidor clásica: un frontend de una sola página que habla por HTTP con un backend propio, que es el único componente con acceso a la base de datos y a los servicios externos. Ni Cloudinary ni OpenAI reciben datos de beneficiarios directamente del navegador. 

flowchart LR
  U["Navegador (React SPA)"] -->|"HTTPS + ID token Firebase"| API["Backend Express (Node.js)"]
  U -->|"login / sesión"| FBAuth["Firebase Authentication"]
  API -->|"lee / escribe"| FS[("Firestore")]
  API -->|"sube foto de evidencia"| CLD["Cloudinary"]
  API -->|"herramientas del asistente"| API
  API -->|"razona sobre los datos ya obtenidos"| AI["OpenAI (gpt-4o-mini)"]
  U -. "PWA: cola local sin conexión" .-> IDB[("IndexedDB")]
  IDB -. "sincroniza al volver la conexión" .-> API

Backend

  • Node.js + Express, organizado por módulo (routes/ → controllers/), con Firestore (Firebase Admin SDK) como única base de datos.
  • Autenticación: cada request de escritura exige un ID token de Firebase Authentication válido (middleware/auth.js); los indicadores y el asistente además exigen rol administrador, verificado contra Firestore en cada llamada.
  • Evidencia fotográfica: multer recibe el archivo en memoria y lo sube a Cloudinary; solo la URL resultante se guarda en Firestore.
  • Asistente de IA: LangChain.js sobre un modelo de OpenAI configurable (por defecto gpt-4o-mini). Sus "herramientas" son las propias rutas internas del backend, llamadas con el token del usuario que pregunta — nunca toca Firestore directamente ni tiene permisos propios.

Frontend

  • React 19 + TypeScript sobre Vite, con react-router-dom para las rutas y una vista distinta según haya o no sesión iniciada.
  • Progressive Web App: un service worker (vite-plugin-pwa) precachea la aplicación y IndexedDB (librería idb) guarda una copia local de cada ficha y una cola de operaciones pendientes cuando no hay conexión.
  • Google Maps JavaScript API para la captura de ubicación al registrar un beneficiario.
04

Estructura de datos

Firestore es una base documental: beneficiarios, programas y usuarios son colecciones de nivel raíz; familiares, participaciones, atenciones y seguimientos viven como subcolecciones dentro de cada beneficiario, para que todo su historial quede agrupado bajo un mismo documento padre.

05

Tipos de usuario

Hay tres niveles de acceso. La separación no es solo visual: el backend exige el rol correcto en cada endpoint (requireAuth / requireAdmin), así que ocultar un botón en la pantalla no es lo único que protege un dato.

Visitante público sin sesión iniciada
  • Ve la página de inicio del proyecto: misión, líneas de trabajo, cómo acceder a un programa, impacto esperado y canales de contacto.
  • No ve ningún dato de beneficiarios ni cifras internas. Un único botón: iniciar sesión.
Encuestador usuarios/{uid}.rol = "encuestador" · asignado automático al primer ingreso
  • Buscar, registrar y editar beneficiarios; evitar duplicados por documento.
  • Registrar familiares y vincular a programas.
  • Registrar atenciones, ayudas y seguimientos, con evidencia fotográfica.
  • Consultar la ficha consolidada de cualquier beneficiario.
  • No ve el tablero de indicadores agregados ni el asistente de IA.
Administrador usuarios/{uid}.rol = "administrador" · se otorga solo a mano en Firestore
  • Todo lo que puede hacer un encuestador.
  • Tablero de indicadores agregados (beneficiarios únicos, participaciones por programa, atenciones registradas, seguimientos con acción pendiente), exportable a PDF.
  • Asistente virtual de IA para resumir historiales y consultar indicadores por chat.
